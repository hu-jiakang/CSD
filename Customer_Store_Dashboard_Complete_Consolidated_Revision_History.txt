V23.2 - Customer/Store Hierarchy Source Separation

1. STORE HIERARCHY
   - Store Sub-Region comes ONLY from Store Department (F_RTA_Department).
   - Store Region comes ONLY from Store Region (F_RTA_Region).
   - Store District comes ONLY from the Store Region -> Department Territory lookup.
   - Customer Region/District is not used to place Stores in the Store hierarchy.

2. CUSTOMER HIERARCHY
   - Customer Region comes ONLY from Customer F_RTA_Region.
   - Customer District comes ONLY from the Territory mapped from Customer F_RTA_Region.
   - Sales Department (FSALDEPTID) is NOT used as a Customer hierarchy fallback.
   - Store Region/District is NOT used as a Customer hierarchy fallback.

3. WHY
   - A Store and its linked Customer can legitimately belong to different geographic
     assignments. Each tab must therefore follow its own master-data geography.
   - This prevents a Customer from being moved to a District based on its linked
     Store or Sales Department.

4. ACCESS CONTROL
   - Existing authorization and access filtering are preserved.
   - This revision changes only the source used to derive Customer/Store geographic
     hierarchy; it does not broaden user access.

Purpose
-------
Correct the dashboard API so the frontend can explicitly request the Customer
view. The previous dashboardSummaryController did not forward req.query.view

levels such as Sales Department/Sub-region to appear in the Customer tab.

------------------
STORE TAB:

CUSTOMER TAB:

Customer Region, or Customer hierarchy levels.

Sales Department is not a Customer hierarchy level and is not used to derive
Customer geography.

Changes
-------
1. dashboardSummaryController now reads req.query.view and passes it to
   dashboardSummaryService.getSummary().
2. dashboardSummaryService already enforces the Customer hierarchy as only:
   district -> region -> customer.
3. Store hierarchy remains district -> region -> subRegion -> store.

   referenced without being assigned.
5. No hard-coded geographic values were added.
6. Existing authorization, exclusions, inactive handling, binding logic,
   customer-store linkage, DSTDLR, and export behavior are preserved.

Expected API behavior
---------------------
GET /api/dashboard-summary?view=customers
  -> Customer root: District rows

GET /api/dashboard-summary?view=customers&level=region&parentValue=<district>
  -> Region rows under that Customer District

GET /api/dashboard-summary?view=customers&level=customer&parentValue=<region>

V24.54.2 - Authentication Database Separation

Purpose
-------
Restore the established EKSBASE-style separation between application authentication data and Kingdee-sourced dashboard data.

Changes
-------
1. Kingdee SQLite remains Backend/data/kingdee.db.
   - Customer data
   - Store/Warehouse data
   - Binding data
   - Department enrichment data
   - Synchronization logs

2. Authentication SQLite is Backend/data/customer-store-dashboard.db.
   - credentials
   - sessions

3. Existing credential hashes and sessions in customer-store-dashboard.db are preserved.

5. authService.js uses the authentication database when invalidating employee sessions after password reset.

Compatibility
-------------
No Customer, Store, Binding, Department enrichment, access-control, password hashing, DingTalk SSO, or dashboard business logic was intentionally changed by this revision.

The Kingdee database may still contain legacy credentials/sessions tables created by previous versions. They are no longer used by authentication and are retained to avoid destructive schema changes.

V24.6 - Customer Active Store Count Scope Fix

Customer tab rule:
HQ -> District -> Region -> Customer -> Store.

Active Customer Store Count is calculated from the full Customer->Store relationship set for the active Customers within the user's Customer access scope. The linked Store's own District, Region, or Sub-region does NOT filter this count.

Only valid Store Codes are counted, each Store Code is counted once per Customer, and the Store must be active according to the Store master (store.disabled === false).

Store tab remains strictly Store-basis:
HQ -> District -> Region -> Sub-region -> Store.

No changes to authentication, authorization, search, export, binding, DSTDLR, exclusions, active Customer rules, or Store hierarchy.
